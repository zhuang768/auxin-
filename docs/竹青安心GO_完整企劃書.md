## 0. 一頁決策摘要

### 核心建議

不要把作品做成一個功能很多、卻沒有明確主角的補助網站，也不要把成敗綁在政府 LINE 官方帳號的 API 權限上。應把「竹青安心GO」收斂成一個可被評審親手操作的公共數位服務：

> 青年準備把內容送進 ChatGPT、Claude、Gemini 等 AI 工具時，系統在資料離開裝置前，於本機辨識可能的個資與機密資訊，解釋風險並提供安全改寫；同時用最少、不可回推出原文的資料，協助青年完成資安學習，並讓市府看見申請、審查與通知狀態。

### 三層產品

1. **安心防護擴充功能（核心）**：送出前攔截、風險解釋、一鍵遮蔽、安全改寫；原始 Prompt 不上傳。
2. **補助服務入口（流程）**：資格預檢、申請進度、安全教材、案例摘要、完成證明與通知偏好。
3. **市府審查工作台（落地）**：案件狀態、缺件提示、人工覆核、匿名統計與通知派送；看不到民眾的原始 Prompt。

### LINE 的正確位置

LINE 應是「通知與入口介面之一」，不是唯一產品，也不是核心技術。競賽 Demo 可以使用團隊自己的 LINE Developers 測試頻道，或用完整的模擬介面展示訊息格式；不得宣稱已接上新竹市政府正式帳號。後端需設計成通路轉接器，未來可接 LINE、Email、簡訊與站內通知。

### 兩天最小可行成果

- 可操作的 Chrome 擴充功能，能在示範對話頁攔截至少五類敏感資料。
- 可走完「申請 → 安全學習 → 防護操作 → 市府審查 → 收到通知」的完整流程。
- 一頁式 AI 安全使用懶人包，以及 3 至 5 則有來源的重大案例摘要。
- 可離線展示的合成資料、Demo 模式與清楚標示。
- 基礎測試、README、架構圖、隱私說明、8 分鐘簡報與備援影片。

### 競賽策略

官方評分為創新性 30%、實用可行性 30%、使用者體驗 20%、市場價值 20%。產品設計、Demo 順序與簡報都必須直接回應這四項，而不是只展示程式碼。

## 1. 題目與競賽邊界

### 1.1 官方題目理解

本題延伸自新竹市「AI 領航青年數位工具補助計畫」，鼓勵青年使用 AI 與數位生產力工具，同時降低個資與資訊安全風險。市府公開說明提到的方向包含：

- AI 資安宣導。
- 補助申請流程優化。
- LINE 官方帳號整合。
- AI 安全使用教材設計。
- AI 資安素養推廣。

這些是期待團隊回應的問題面向，不代表所有功能都必須以 LINE 實作，也不代表網站、擴充功能或特定模型被指定為唯一技術。作品應提出一套可操作、可落地、對青年與承辦人員都有價值的整體服務。

### 1.2 本企劃採用的解題範圍

本方案同時解兩個核心問題：

1. **青年端的 AI 使用風險**：使用者常在不自覺的情況下輸入身分證字號、聯絡資訊、付款資訊、地址、工作機密或客戶資料。
2. **市府端的補助服務成本**：申請人不確定資格、文件與進度，承辦人員反覆回答、補件、更新狀態與宣導安全注意事項。

方案不把「監控青年用了多少小時、送了多少 Prompt」當成補助核銷依據，因為這會增加蒐集、造假與隱私風險。競賽原型只證明使用者完成安全教育、啟用防護與完成必要流程，不蒐集原始對話。

### 1.3 明確非目標

- 不直接接管或修改新竹市政府正式 LINE 官方帳號。
- 不要求使用者上傳真實身分證、信用卡、住址或私人 AI 對話。
- 不宣稱可百分之百辨識所有個資或阻止所有外洩。
- 不將前端自行產生的雜湊宣稱為不可偽造的數位簽章。
- 不將 Demo 模擬狀態、假資料或未串接服務宣稱為真實上線功能。
- 不在黑客松期間建立完整付款、撥款、政府身分驗證或生產級防詐系統。

## 2. 問題定義與洞察

### 2.1 目標使用者

#### 主要使用者 A：申請數位工具補助的青年

- 年齡與設籍資格依當年度官方補助公告。
- 可能首次申請政府補助，不熟悉文件與流程。
- 使用生成式 AI，但不一定理解資料會離開裝置、被第三方處理或保留。
- 需要低負擔、即時且不羞辱使用者的提醒。

#### 主要使用者 B：青年發展中心承辦人員

- 需要處理資格、缺件、進度詢問、核銷與安全宣導。
- 不能因導入新工具而增加更多人工複製貼上與多平台切換。
- 需要看見案件狀態與群體風險趨勢，但不應看見個人的原始 AI 對話。

#### 次要使用者

- 市府政策與資訊安全人員。
- 協助申請的學校、社群、青年組織。
- 未來採用相同治理模式的其他縣市。

### 2.2 現況痛點

| 情境 | 現況痛點 | 直接後果 |
|---|---|---|
| 申請前 | 資格、可補助項目、應備文件分散 | 重複詢問、填錯、放棄申請 |
| 使用 AI | 使用者在送出後才意識到含有個資 | 個資、商業機密或帳務資訊外洩 |
| 安全教育 | 教材多為靜態文字，與實際行為分離 | 看過不等於會做 |
| 審查與補件 | 案件狀態與通知分散 | 承辦與申請人來回溝通 |
| 成效評估 | 容易走向追蹤使用時數與內容 | 產生監控疑慮、擴大資料責任 |

### 2.3 How Might We

> 我們如何讓青年在幾乎不改變原本 AI 使用習慣的情況下，於敏感資料離開裝置之前得到可理解、可執行的保護；同時讓市府能用最少資料提供補助服務與評估政策成效？

### 2.4 設計原則

1. **風險發生前介入**：提醒必須發生在按下送出之前。
2. **本機優先**：原始 Prompt 與敏感內容預設不離開裝置。
3. **最少蒐集**：市府只取得辦理服務必要的資料。
4. **可解釋、可選擇**：不只是封鎖，還要說明原因並提供安全替代方案。
5. **人可覆核**：高風險或爭議狀況保留人工判斷。
6. **通路無關**：LINE 是可用入口，不是唯一入口。
7. **誠實展示**：真實、模擬與未完成項目清楚標示。
8. **無障礙與包容**：行動裝置、鍵盤、色覺與低數位熟悉度都納入設計。

## 3. 解決方案

### 3.1 產品定位

「竹青安心GO」不是另一個 AI 聊天機器人，而是架在補助服務與既有 AI 工具之間的安全層。它把一次性的宣導內容轉成可操作的行為護欄，並把補助流程變成透明、可追蹤、可從不同通路接入的服務。

### 3.2 核心價值主張

#### 對青年

- 不必換掉原本使用的 AI 工具。
- 在送出前知道「哪一段有風險、為什麼、如何改」。
- 不上傳原始對話也能完成安全學習與取得完成證明。
- 從資格預檢到補件、審查與結果通知都有一致入口。

#### 對市府

- 減少常見資格與文件問題的重複回覆。
- 把安全宣導嵌入使用情境，而非只提供 PDF。
- 用匿名、彙總指標了解常見風險類型，不接觸原始 Prompt。
- 通知管道可逐步擴充，不受單一平台綁定。

### 3.3 差異化

| 一般補助網站 | 一般個資掃描器 | 竹青安心GO |
|---|---|---|
| 只處理申請表單 | 只顯示警告 | 串連申請、教育、防護、審查與通知 |
| 宣導與行為分離 | 常將文字送到雲端分析 | 預設於本機辨識，原文不離開裝置 |
| 通知依賴單一管道 | 與政府服務無關 | LINE、Email、站內通知可替換 |
| 承辦看不到安全成效 | 缺少政策視角 | 僅上傳匿名彙總指標供政策改進 |

## 4. 完整服務流程

### 4.1 青年端流程

1. 從官方網站、LINE 圖文選單、QR Code 或活動頁進入服務。
2. 先看清楚的補助資格與應備文件預檢，不必立即登入。
3. 進入 Demo 時使用合成資料；正式服務才透過政府既有申辦與身分機制。
4. 閱讀最小必要蒐集與隱私說明，選擇通知方式。
5. 完成 3 分鐘互動安全導覽：辨識個資、理解外洩、練習改寫。
6. 安裝或啟用安心防護擴充功能。
7. 在示範 AI 對話頁輸入一段含假身分證、電話、Email 或地址的文字。
8. 系統在本機攔截，標示風險並提供三個選項：返回修改、一鍵遮蔽、理解風險後仍送出。
9. 若選擇安全改寫，只把遮蔽後內容送出；原始內容留在裝置記憶體中並立即清除。
10. 入口顯示安全學習完成、申請狀態與待辦事項。
11. 市府更新案件狀態後，使用者從站內通知收到訊息；若已設定 LINE 測試頻道，也可收到同一事件的 LINE 訊息。

### 4.2 市府端流程

1. 登入審查工作台。
2. 查看待審件數、缺件類型與時間順序。
3. 開啟個案，只看到申請必要欄位與安全學習完成狀態。
4. 不顯示任何原始 Prompt、遮蔽前文字或瀏覽紀錄。
5. 選擇核准、請補件或退回，輸入結構化原因與補充說明。
6. 系統產生通知事件，依使用者偏好派送到站內、LINE、Email 或簡訊轉接器。
7. 工作台顯示匿名彙總：風險類別分布、攔截後選擇、教材完成率與案件處理時間。

### 4.3 LINE 整合策略

#### 競賽版

- 使用團隊自有 LINE Developers 測試 Provider 與 Messaging API，僅傳送合成 Demo 資料。
- 若來不及取得頻道或公開 HTTPS 端點，使用可操作的「通知轉接器模擬器」，展示送出事件、訊息內容與成功狀態。
- 簡報明確寫「LINE PoC／未接政府正式帳號」。

#### 正式版

- 由市府決定是否整合既有官方帳號、LIFF 或改用政府數位申辦平台。
- 經正式權限與資安審查後，再接入帳號綁定與 Webhook。
- LINE 只承載低敏感度狀態通知；詳細個資與文件仍回到受控的政府申辦頁查看。

## 5. 功能規格

### 5.1 P0 必做

#### A. 本機個資防護

- 支援 Demo Chat，並以適配器方式支援 ChatGPT、Claude、Gemini。
- 至少偵測：台灣身分證字號、手機號碼、Email、信用卡號、地址關鍵特徵。
- 身分證使用格式與檢核碼驗證，信用卡使用 Luhn 檢核，降低誤判。
- 送出前出現非阻塞式風險抽屜，逐項說明類型與風險。
- 提供一鍵遮蔽：例如 `A123456789` 轉為 `[身分證字號已移除]`。
- 提供安全改寫，競賽版先採規則式樣板；不得為了改寫把原文送到外部模型。
- 允許覆寫，但需二次確認；只記錄風險類別與結果，不記錄原文。
- 所有辨識預設在本機執行。

#### B. 補助入口

- 資格與文件預檢。
- 申請 Demo 表單，欄位全部使用合成資料。
- 進度時間軸：草稿、已送出、審查中、需補件、已核准、已完成。
- 通知偏好設定與站內通知。
- 清楚的隱私摘要與完整說明。

#### C. 安全教育

- 一頁式安全懶人包，可列印與下載。
- 3 至 5 則案例摘要，每則包含事件、風險、可採取行動與來源連結。
- 3 題互動情境測驗，立即說明答案。
- 完成證明只表示完成課程與基本操作，不代表使用者永遠安全。

#### D. 市府工作台

- 案件列表、狀態篩選與個案頁。
- 核准、補件、退回與通知動作。
- 匿名安全事件統計，不顯示原始 Prompt。
- Demo 管理員驗證，不能以公開無密碼頁面直接操作。

#### E. Demo 模式

- 一鍵重設展示資料。
- 所有假資料標示「Demo／合成資料」。
- 不依賴外部網路也能走核心流程。
- 準備錄影備援，避免現場網路或瀏覽器更新造成失敗。

### 5.2 P1 應做

- 使用伺服器簽發短期 nonce 與 HMAC 的完成憑證，取代純前端雜湊。
- LINE 通知轉接器與團隊測試頻道。
- 文件缺件規則與結構化補件原因。
- 鍵盤操作、ARIA 標籤、對比與行動版版面。
- 事件日誌的留存期限與刪除機制。
- 自動化測試與簡易 CI。

### 5.3 P2 加分功能

- 發票或收據的本機 OCR 預檢，但不得自動做最終核定。
- 多語系摘要。
- 政策成效儀表板與匯出。
- 可由市府自訂敏感詞，例如尚未公開的專案名稱。
- 行動版 Share Sheet 或 PWA 快捷入口。

### 5.4 本次應刪除或降級的舊功能

- 移除以 20 小時、30 則 Prompt 作為補助達標依據的設計。
- 移除「連續使用幾天」等容易鼓勵監控的分數。
- 將「隱私守護分數」改為清楚的「安全設定與學習完成度」，不對個人貼風險標籤。
- 將「防弊」降為完成憑證的完整性驗證，不宣稱能防止所有造假。
- 不在工作台提供原始對話查看功能。

## 6. 技術架構

### 6.1 兩日競賽建議技術棧

- 後端：FastAPI。
- 資料庫：SQLite（Demo），保留 PostgreSQL 遷移介面。
- 前端：優先延用現有 Jinja／HTML／CSS／JavaScript；除非團隊已熟悉 React，否則不為重寫而重寫。
- 擴充功能：Chrome Manifest V3。
- 測試：pytest、FastAPI TestClient、JavaScript 純函式測試；若時間允許加 Playwright。
- 部署：競賽現場以本機為主，另準備受控的 HTTPS Preview；未經核准不做正式生產部署。

### 6.2 元件

1. **Extension Content Adapter**：定位各 AI 網站的輸入框與送出事件；網站差異封裝在 adapter 中。
2. **Local Detection Engine**：正規表示式、檢核碼、敏感詞與風險分類；輸入與比對結果不離開頁面。
3. **Risk Review UI**：呈現命中內容、原因、遮蔽與覆寫選項。
4. **Service Portal**：申請、教材、狀態、通知與個人設定。
5. **Admin Console**：案件處理與匿名統計。
6. **Backend API**：身分與工作階段、案件狀態機、教材完成、通知事件與完成憑證。
7. **Notification Adapters**：站內為預設；LINE、Email、SMS 採同一介面。
8. **Demo Seed**：建立合成使用者、案件、通知與統計資料。

### 6.3 資料流

```text
使用者輸入 Prompt
    ↓
瀏覽器本機偵測
    ├─ 無風險 → 送往原 AI 網站
    └─ 有風險 → 解釋／遮蔽／安全改寫／覆寫
                       ↓
          僅記錄類別、時間、選擇結果
                       ↓
                 後端彙總 API
                       ↓
         市府匿名統計（沒有原始 Prompt）

補助入口 → 案件 API → 審查工作台 → 通知事件 → 站內／LINE／Email
```

### 6.4 建議資料模型

| 實體 | 必要欄位 | 不應保存 |
|---|---|---|
| User | demo_id、通知偏好、同意版本 | AI 對話全文 |
| Application | status、建立時間、必要資格欄位、review_note | 不必要的敏感證件影像 |
| LearningCompletion | module、完成時間、版本 | 測驗中輸入的自由文字 |
| RiskAggregate | category、action、日期區間、匿名計數 | 命中文字、頁面內容、完整 URL |
| Notification | event_type、channel、delivery_status、template_id | 高敏感資訊與完整文件 |
| Attestation | nonce_id、issued_at、expires_at、server_mac | 可逆推出 Prompt 的內容 |

### 6.5 API 草案

| 方法 | 路徑 | 用途 |
|---|---|---|
| POST | `/api/demo/reset` | 重建合成展示資料 |
| POST | `/api/applications` | 建立 Demo 申請 |
| GET | `/api/applications/{id}` | 查詢案件狀態 |
| POST | `/api/applications/{id}/review` | 市府更新案件狀態 |
| POST | `/api/learning/completions` | 記錄教材完成 |
| POST | `/api/risk-events/aggregate` | 上傳不含原文的風險事件 |
| POST | `/api/attestations/challenge` | 取得短期 nonce |
| POST | `/api/attestations/complete` | 由伺服器驗證並簽發完成憑證 |
| POST | `/api/notifications/test` | Demo 通知轉接器 |

### 6.6 狀態機

```text
draft → submitted → under_review
                      ├─ needs_revision → submitted
                      ├─ rejected
                      └─ approved → completed
```

所有狀態轉換必須在後端驗證，前端不可任意跳階。Demo 快捷操作要清楚標示並只在 Demo 模式可用。

## 7. 隱私、安全與威脅模型

### 7.1 資料分類

- **高敏感**：身分證、付款資料、地址、證件影像、原始 Prompt。原型中不進後端。
- **個人資料**：姓名、Email、電話、申請資格。只在服務必要範圍使用。
- **低敏感事件**：命中類別、選擇遮蔽或取消、教材完成時間。可去識別後彙總。
- **公開內容**：懶人包、案例摘要、服務說明。

### 7.2 主要威脅與控制

| 威脅 | 影響 | 競賽版控制 | 正式版增強 |
|---|---|---|---|
| 原始 Prompt 被上傳 | 隱私外洩 | 本機偵測、API schema 禁止原文 | 程式碼稽核、CSP、DLP 測試 |
| 擴充功能權限過大 | 瀏覽資料暴露 | 最小 host permissions、清楚列出支援網站 | 動態權限、商店審查 |
| 前端憑證偽造 | 錯誤核定 | 短期 nonce、後端 HMAC、狀態機 | 受信任裝置或政府身分整合 |
| 管理後台未授權 | 案件遭竄改 | 管理員登入、CSRF 防護、審計事件 | SSO、RBAC、異常告警 |
| LINE 訊息洩密 | 第三方平台看到敏感資料 | 僅發低敏感狀態與安全連結 | 正式 DPIA、訊息範本審查 |
| 正規表示式誤判 | 阻擋正常使用 | 檢核碼、清楚解釋、可覆寫 | 可調規則、匿名回饋 |
| 網站 DOM 改版 | 防護失效 | Demo Chat 保底、adapter 分層 | 自動化瀏覽器測試、版本監控 |
| Demo 假資料混同真實 | 評審誤解 | 全站 Demo 標章、重設按鈕 | 測試與正式環境隔離 |

### 7.3 隱私承諾

1. 原始 Prompt 不送到竹青安心GO伺服器。
2. 不出售、不廣告、不建立個人 AI 使用輪廓。
3. 市府端不顯示個人對話。
4. 使用者可查詢與刪除 Demo 資料。
5. LINE 只傳低敏感度通知。
6. 所有分析數字必須標明「測試資料」「目標值」或「實測值」。

### 7.4 完成憑證的誠實說法

競賽版完成憑證可證明「伺服器曾對一次合法的 Demo 流程簽發記錄，且傳輸後內容未被任意改寫」，但不能證明使用者在真實世界中完全遵守安全行為，也不能取代政府身分驗證或正式防詐系統。

## 8. 使用者體驗與無障礙

### 8.1 介面語氣

- 不使用恐嚇式紅色警報作為唯一訊息。
- 先告知「我們發現可能的個資」，再說明位置、風險與可採取行動。
- 不用「你做錯了」，改用「建議先移除，再安全送出」。

### 8.2 風險抽屜範例

標題：送出前先保護這段資料  
說明：偵測到一組可能的手機號碼。它可能被 AI 服務處理或保留。  
主要按鈕：安全遮蔽後送出  
次要按鈕：返回修改  
第三選項：我了解風險，仍要送出

### 8.3 無障礙要求

- 鍵盤可完成主要操作，焦點順序正確。
- 警示不只依賴顏色，搭配圖示與文字。
- 文字對比至少符合 WCAG AA 的基本方向。
- 表單有 label、錯誤訊息與修正建議。
- 動畫尊重 `prefers-reduced-motion`。
- 手機寬度可閱讀，不以 hover 才能取得資訊。

## 14. 五分鐘 Q&A 題庫

### 為什麼不直接做 LINE Bot？

LINE 很適合通知與入口，但真正的風險發生在青年使用各種 AI 工具時。把防護放在瀏覽器本機，才能跨 ChatGPT、Claude、Gemini；LINE 仍保留為市府既有通路的轉接器。

### 你們真的接上政府 LINE 了嗎？

沒有。競賽版只使用團隊測試頻道或模擬器。正式串接需政府帳號權限、Webhook、資安與隱私審查；我們已把通知介面設計好，取得授權後可接入。

### 本機正規表示式會不會誤判？

會有可能，因此身分證與信用卡加上檢核碼，介面解釋原因且允許使用者返回修改或在理解風險後覆寫。正式版會透過匿名回饋逐步調整規則。

### 如何證明你們沒有偷傳 Prompt？

API schema 不接受原始 Prompt，Demo 可直接檢視 Network 與資料庫；事件只包含類別、動作與時間。正式版還會加入程式碼稽核、內容安全政策與隱私測試。

### 為什麼不追蹤使用時數與 Prompt 數？

它們與補助的真實效益不完全等價，也容易被造假，更會形成監控負擔。我們改以資格、教材完成、必要文件與自願的匿名安全事件衡量。

### 憑證能防止所有造假嗎？

不能。短期 nonce 與伺服器 HMAC 能提高完整性並避免單純改前端數值，但不是政府身分驗證。正式核定仍需既有申辦、文件與人工程序。

### 如何處理手機使用者？

補助入口、教材與通知是響應式 PWA；桌面瀏覽器擴充功能負責最完整的送出前防護。未來可研究行動瀏覽器與系統 Share Sheet，但本次不虛構尚未完成的能力。

## 20. 最終主張

竹青安心GO的競爭力不在於堆出最多頁面，而在於把一道常被忽略的風險，變成評審可以親手感受到的保護：資料還沒離開裝置，系統就已經幫使用者看見、理解並安全改寫；市府仍能完成服務與成效評估，卻不需要看見青年的私人對話。

這個版本同時回應題目的申請流程、LINE 整合、安全教材與資安素養，也透過通路無關、本機優先、最少蒐集與誠實揭露，避免為了 Demo 製造新的隱私問題。兩日競賽的首要任務不是做完整政府平台，而是做出一條可信、流暢、可重複展示的端到端體驗，並清楚說明如何從原型走向正式公共服務。
